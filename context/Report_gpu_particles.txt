## The Verlet Integration Method

Particle-based simulations are widely used to model various physical phenomena such as fluids, gases, granular materials, and plasmas. In this project, each particle follows Newtonian mechanics: for every time step, the total force acting on each particle is computed, then integrated to update its velocity and position. A basic physical model can be written as:
[
m_i d^2 x_idt^2 = _j i F(x_i, x_j),
]
where ( x_i ) and ( m_i ) are the position and mass of particle (i), and (F) represents the pairwise interaction force (e.g., gravitational, repulsive, or Lennard–Jones).

In this project, the time integration is performed using the Verlet integration method, which is widely used in molecular dynamics and particle simulations due to its simplicity. The standard form of the algorithm is:
[
x_i(t + t) = 2 x_i(t) - x_i(t - t) + F_i(t)m_i t^2.
]
Velocities can be estimated, if needed, as:
[
v_i(t) = x_i(t+ t) - x_i(t- t)2 t.
]

At each simulation time step, the core idea of the update loop is to first compute and update the new state of each particle, and then enforce physical constraints through collision handling. The particle velocity is implicitly evaluated using the Verlet-based formulation from the current and previous positions, ensuring numerical stability for the integration. Based on this velocity, boundary collisions with the domain walls and particles-particles collisions are detected and resolved by correcting the particle position and applying a damping factor to simulate energy loss during impacts. After collision handling, the new particle position is computed using the Verlet integration scheme, which combines the current position, velocity, and acceleration.

## CPU Implementations

## Simple Implementation

In our Simple CPU-based implementation, each particle is represented as an object containing its current position, previous position, velocity, and acceleration. The numerical computations for the particle dynamics, including the integration of motion using the Verlet formula are performed entirely within a dedicated solver class.

For visualization, we use the SFML library (Simple and Fast Multimedia Library), which provides a lightweight interface for rendering 2D graphics and handling user input. SFML retrieves the computed particle states from the CPU and sends them to the GPU solely for display purposes; no physics or numerical calculations are performed on the GPU. Thus, all simulation computations remain CPU-only.

Our algorithm 1 has a computational complexity of O(n^2), where n is the number of particles (because of the handle collision loop), which makes it very demanding in terms of processing time and memory usage for large particle systems.

## Refined Optimizations : Hash Grid Computation

A first simple improvement of our CPU implementation is the use of a spatial hashing technique, commonly referred to as a hash grid, to accelerate collision detection. Instead of checking every particle against all others, the simulation domain is divided into a uniform grid of cells, and each particle is assigned to a cell based on its position. Collisions are then only checked between particles within the same cell or in neighboring cells. This significantly reduces the number of pairwise checks while preserving accuracy, providing a simple yet effective way to improve the performance of the collision detection step without modifying the core solver logic.

## Parallelization Opportunities

Our numerical scheme is particularly well-suited for GPU execution, as the update of each particle depends only on its own state and on locally evaluated interaction forces, enabling a high degree of fine-grained data parallelism.
On the GPU, each particle can be mapped to a single CUDA thread, allowing thousands of particle updates to be computed simultaneously.
This mapping naturally maximizes occupancy when the number of particles is large, which is what we want.

The inner interaction loop remains the main computational bottleneck and therefore the primary target for GPU acceleration.
Several optimization strategies can be explored to further improve performance:

- Parallel particle updates: particle integration (position, velocity, and acceleration updates) can be executed independently for each particle, making it ideal for massive parallel execution on the GPU.

- Memory access optimization: particle data can be stored in a structure-of-arrays (SoA) layout to ensure coalesced global memory accesses, significantly improving memory throughput compared to an array-of-structures (AoS) layout.

- Shared memory usage: for interaction computations, blocks of neighboring particle data can be loaded into shared memory, reducing global memory accesses and hiding memory latency during force accumulation.

- Computation–rendering interoperability: the CPU implementation relies on the SFML graphical library for visualization.
On the GPU, particle positions can be stored directly in an OpenGL Vertex Buffer Object (VBO) and updated using CUDA–OpenGL interoperability, eliminating costly CPU--GPU memory transfers and enabling real-time rendering directly from GPU-computed data.

Simple CUDA Implementation

We will now present a first GPU-based implementation of the particle simulation using CUDA.
The objective is not yet to achieve optimal performance, but rather to demonstrate how the
original CPU algorithm can be mapped onto the GPU execution model in a clear and efficient way.
This simple implementation also serves as a baseline for the more advanced optimizations
introduced in the next chapter.

## Overall GPU Architecture

The simulation is fully executed on the GPU, while the CPU is only responsible for initialization
and kernel launches. The implementation is divided into two main components: a GPUSolver,
which handles the physical simulation, and a GPURenderer, which manages visualization
through OpenGL.

Each CUDA thread is associated with a single particle. At each time step, the GPU performs the following operations:

- update particle positions using the Verlet integration scheme,

- resolve collisions with the simulation boundaries,

- handle particle--particle collisions,

- write updated positions directly into an OpenGL vertex buffer for rendering.

This design allows the entire simulation loop to remain on the GPU, minimizing data transfers between the CPU and the GPU.

## Data Structures and Memory Layout

Particles are stored in a contiguous array allocated in global GPU memory. Each particle is
represented by its current position, previous position, velocity and
acceleration.

Several physical parameters remain constant throughout the simulation, such as the
time step, particle radius, gravity, and the simulation bounds.
These parameters are stored in CUDA constant memory.

Since constant memory is cached and optimized for broadcast access, this choice significantly
reduces memory access latency when the same values are read by all threads.

## Kernels Implemented

## Position Update and Boundary Collisions

The first CUDA kernel updates particle positions using a Verlet integration scheme. Each thread
operates on a single particle, making this kernel embarrassingly parallel.

The position update is given by:
[
x_t+ t = 2x_t - x_t- t + a_t t^2,
]

Boundary collisions with the simulation domain are handled within the same kernel. When a particle
exits the allowed domain, its position is clamped and its velocity is reflected with a damping
factor. Grouping integration and boundary handling in a single kernel reduces
kernel launch overhead and avoids unnecessary memory accesses.

## Particle--Particle Collision Kernel

Particle--particle interactions are handled by a second CUDA kernel. Each thread is responsible
for resolving collisions involving one particle, looping over all other particles to detect
overlaps.

This approach leads to a quadratic computational complexity of O(N^2), which quickly
becomes the main performance bottleneck as the number of particles increases. Nevertheless, this
naive strategy is sufficient for a first GPU implementation and allows a
direct comparison with the CPU version.

## CUDA--OpenGL Interoperability

To render the simulation efficiently, particle positions are written directly into an
OpenGL Vertex Buffer Object (VBO). The buffer is registered with CUDA using
CUDA--OpenGL interoperability, allowing CUDA kernels to access it directly.

This approach avoids costly CPU--GPU memory transfers and ensures that rendering consumes the
most up-to-date particle positions. The visualization pipeline therefore remains
entirely on the GPU, significantly improving performance and scalability.

## GPU Simulation Loop

At each simulation step, the following sequence of CUDA kernels is executed:

- position update and boundary collision kernel,

- particle--particle collision kernel,

- kernel writing particle positions to the OpenGL VBO.

Since the application is written in C++, CUDA kernels cannot be called directly from the
host code. A dedicated C++ wrapper is therefore used to launch the kernels,
manage execution configuration (grid and block sizes), and handle synchronization.
This wrapper provides a clean interface between the CPU-side simulation loop and the
GPU-side computation while preserving code modularity and readability.

## Thread and Block Dimensions

The CUDA kernels are launched using a one-dimensional grid configuration, where each thread
is responsible for processing a single particle.

This ensures that all particles are covered, even when the particle count is not a multiple of
the block size.

A fixed block size (blockSize.x) is used for all kernels, providing a consistent execution
configuration across the different computation stages (position update, collision handling, and
VBO transfer).
In practice, a block size of 256 threads was selected, which is a well-established
compromise on modern NVIDIA GPUs.

All kernels therefore share the same launch configuration:
updatePositionsKernel, handleCollisionsKernel, and
copyToVBOKernel.

## Limitations of the Simple Implementation

While this CUDA implementation demonstrates the feasibility of executing the simulation entirely
on the GPU, it suffers from several limitations:

- the particle--particle collision kernel scales quadratically with the number of particles,

- memory access patterns are not optimized for coalescing,

- shared memory is not yet exploited,

- potential write conflicts are not explicitly handled.

These limitations
highlight the necessity of more advanced GPU-oriented optimizations, which are introduced and
evaluated in the next chapter.

Bottlenecks Optimizations

We will now try to improve the performance of the initial GPU implementation
and presents two successive optimization strategies. Each optimization aims at improving scalability
and computational efficiency while highlighting the practical limitations identified in the previous part.

## Identification of the Main Bottleneck

Although our program now exhibits a high degree of parallelism, its performance is limited by:

- excessive global memory accesses,

- poor data reuse across threads.

These observations motivated the introduction of memory-level and algorithmic optimizations.

## Memory-Level Optimization: Shared Memory and Coalesced Accesses

## Motivation

The first optimization focuses on reducing global memory traffic by improving data locality.
Since multiple threads repeatedly access neighboring particle data, caching this information in
shared memory can significantly reduce memory latency.

## Optimized Collision Kernel

Particles are processed in tiles, where each thread block loads a subset of particles into
shared memory. Each thread then computes collisions between its assigned particle and the particles
stored in shared memory.

This approach offers several advantages.
While the asymptotic complexity remains O(N^2), the constant factor is significantly
reduced, leading to noticeable performance gains for moderate particle counts.

Despite these improvements, the quadratic nature of the algorithm remains the primary scalability
limitation.

## Algorithmic Optimization: Spatial Hash Grid

## GPU-Oriented Implementation

On the GPU, the spatial hash grid must be constructed and queried in a fully parallel manner.
Each particle independently computes its cell index from its position and writes this
information to a dedicated array.

Particles are then sorted by cell index, allowing particles
belonging to the same cell to be stored contiguously in memory. This layout enables efficient
range-based access, where each cell is represented by a start and end index in the sorted particle
array.

Collision detection is performed by having each thread iterate only over particles contained in
the neighboring cells of its own cell.

## GPU-Specific Challenges

While the spatial hash grid effectively reduces computational complexity, its GPU implementation
introduces several non-trivial challenges.

First, collision resolution requires concurrent updates to particle positions. When
multiple threads attempt to correct overlaps involving the same particle, race conditions
naturally arise.
Second, attempts to combine the hash grid with shared memory optimizations led to
non-physical behaviors, including:

- asymmetric collision responses,

- artificial energy gain or dissipation,

- particle clustering and numerical jittering.

These artifacts stem from inconsistent update ordering and the lack of a global synchronization
mechanism within a single kernel launch.

## Design Trade-offs

To preserve physical stability and determinism, the final implementation with the Hash Grid prioritizes
correctness over raw performance. Collision resolution is therefore performed using
carefully controlled updates in global memory, avoiding aggressive shared memory usage.
These experiments highlight a key trade-off in GPU programming between performance,
algorithmic complexity, and numerical stability.

## Execution Time Analysis

The performance results presented in those figures highlight clear differences
between the three GPU-based implementations as the number of particles increases.

The GPU_Simple implementation, which consists of the direct port of the CPU algorithm
to the GPU without major optimizations, exhibits a smooth and stable increase in CPU frame time
as particle count grows, reflecting the expected linear scaling of the workload.

In contrast, the GPU_Hash implementation, which introduces a spatial hash grid
for collision handling, shows high variability in CPU frame time, with frequent spikes
appearing beyond approximately 5,000 particles. This behavior could be caused by
irregular memory accesses and increased synchronization overhead, leading to a sharp FPS drop
in dense particle regimes.

Finally, the GPU scalability plot highlights the benefits of GPU parallelism.
For all implementations, the per-particle cost decreases as the number of particles increases,
confirming effective GPU utilization. However, GPU_Optimized achieves the
lowest GPU time per particle, especially in the high-particle regime, indicating better
memory efficiency and occupancy.

## GPU Resource Utilization

These focuses on the GPU resources data reveal significant performance differences across our different
GPU implementation strategies for particle simulations.

The GPU_Simple implementation
exhibits consistently high memory consumption at approximately 490 MiB throughout execution,
while achieving near-complete GPU utilization (95--98%) after an initial ramp-up period.

The GPU_Hash implementation
demonstrates a substantial reduction in memory usage to roughly 420 MiB, corresponding
to a 14% improvement over the simple approach. This gain comes with
reduced GPU utilization, fluctuating between 65--85% with noticeable volatility.
This behavior indicates irregular memory access patterns and potential thread divergence introduced
by the hash grid.

Most notably, the GPU_Optimized implementation achieves the best overall balance
by maintaining memory consumption in the 410--420 MiB range while sustaining high GPU
utilization between 85--95%.
The resulting utilization is both high and stable, indicating the successful removal of memory
bottlenecks without introducing thread divergence. The memory--utilization scatter plot shows
tight clustering with consistently high utilization, highlighting the superior stability
of this approach.
