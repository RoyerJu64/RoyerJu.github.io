## Introduction

Diffusion-based generative models rely on an iterative denoising process
that requires repeated evaluations of a neural network.
In large-scale applications such as image or audio generation,
this structure leads to significant computational costs,
often obscured by architectural complexity.

In this work, we deliberately focus on a minimal implementation,
named tiny-diffusion,
designed for pedagogical clarity and experimental simplicity.
By operating on low-dimensional 2D datasets and using a simple MLP-based model,
this implementation provides a controlled environment
for detailed performance analysis.

The objective of this report is not to improve generative quality,
but to analyze the computational behavior of the tiny diffusion model implementation.
Specifically, we aim to:

[leftmargin=*]

- characterize the runtime structure of training and sampling,

- identify performance bottlenecks at multiple abstraction levels,

- compare complementary profiling tools,

- derive optimization insights grounded in empirical measurements.

## Model overview (Tiny Diffusion denoiser)

Our implementation targets a minimal diffusion-model training setup on 2D point datasets. The denoiser is an MLP that takes as input a noisy point x_t R^2 and a discrete timestep t 0, ,T-1. Each coordinate and the timestep are mapped to positional embeddings, concatenated, and processed by a residual MLP. The model outputs a 2D vector R^2 corresponding to the predicted noise component at the current timestep. During training, batches of clean samples x_0 are corrupted by sampling Gaussian noise and generating x_t using a noise scheduler; the denoiser is trained with an MSE loss between and .

## Code Structure and Execution Flow

The core DDPM logic of this project lives in DDPM.py: it contains the training loop, the optional sampling routine, and the glue code that connects the model with the noise scheduler and the optimizer. The remaining modules mostly serve supporting roles (dataset generation/loading, utilities for embeddings, plotting, and profiling), so in what follows we focus on the execution flow that determines both learning behavior and runtime characteristics.

Figure summarizes this flow. After a short initialization phase (argument parsing and component instantiation), execution enters the training loop, which is the dominant workload throughout the run. Each iteration draws a minibatch of clean points x_0 and trains the MLP to predict the injected Gaussian noise: a timestep t is sampled, a noisy point x_t is constructed using the scheduler’s forward diffusion rule, the model predicts =MLP(x_t,t), and the parameters are updated by minimizing MSE( , ). The optional sampling block (controlled by a flag and typically triggered at a fixed interval) does not replace training; instead it provides a periodic qualitative check by starting from pure noise x_T N(0,I) and iterating the scheduler’s reverse step down to a generated x_0. Importantly, whether sampling is executed or skipped, the control flow rejoins at the output stage and then continues to the next iteration, which is exactly what the loop-back arrow in Figure is meant to make explicit.

## Profiling Methodology

This section summarizes the profiling tools used in our optimization workflow and how each tool is applied to the ddpm.py training workload. We combine system-level benchmarking for robust end-to-end runtime measurement and Python-level profiling to localize interpreter and orchestration overhead. Framework-level profiling (PyTorch Profiler) is planned but not yet integrated into the reporting pipeline.

## Hyperfine (System-level benchmarking)

Hyperfine measures end-to-end wall-clock execution time by repeatedly running a full command, capturing both computation and any runtime overhead (startup, Python orchestration, progress display, etc.) as observed externally. Because it executes the complete program multiple times, it provides statistically meaningful estimates of typical runtime and variability. All Hyperfine benchmarks use the same invocation settings:

[leftmargin=*]

- Repetitions: -r 5

- Warmup runs: --warmup 2

- Time unit: --time-unit second

Hyperfine returns summary timing statistics over the repeated executions, including (at minimum) the mean runtime, standard deviation, median, minimum and maximum runtime, and the list of measured run times.

## cProfile (Python-level profiling)

cProfile measures function-level execution inside the Python interpreter. It attributes time to Python function calls (including call counts) and reports both self time (time spent in the function body) and cumulative time (time including callees). This makes it suitable for identifying Python-side hotspots such as excessive call overhead, iterator costs, and high-level training-loop orchestration. We run cProfile through the standard module entrypoint:
python -m cProfile -o <stats> <command>. For interpretation, we generate a top-functions summary by sorting by tottime (self time) and reporting the top 50 entries.

## Memory profiling (RSS via memory_profiler
)

We use memory profiling to estimate the process-level memory footprint of our workloads. The reported metric is RSS (resident set size) in MiB, i.e., the amount of physical memory currently used by the process. We summarize memory behavior using peak RSS over the profiled region and an RSS delta that captures the maximum observed increase during execution (a proxy for transient allocation pressure). In our current setup, memory profiling is applied to the training loop only (the main training function), so the reported values characterize memory usage during training rather than during standalone sampling or other auxiliary phases.

## PyTorch Profiler (Framework-level profiling)

While our previous profiling approaches (memory profiling, Hyperfine, and cProfile) focused on identifying computational bottlenecks and memory usage patterns in the code implementation, we employed PyTorch Profiler for a complementary purpose: systematic hyperparameter benchmarking. This profiling methodology addresses a fundamentally different question—not where the code spends time, but rather which configuration yields the optimal balance between training efficiency and model performance.

## Baseline Benchmark

Our baseline benchmark is the reference measurement used to quantify all subsequent optimizations. It focuses on the training workload only. We explicitly remove (i) the sampling loop and (ii) progress tracking (tqdm) from the baseline measurement, because both were mainly used for evaluation/visual checks and introduce additional control-flow and monitoring overhead that makes training performance changes harder to interpret.

## Data Optimization: Reduced Input-Pipeline Overhead

To reduce non-compute overhead inside the training loop, we modified the input pipeline so that batches are drawn directly from the in-memory tensors backing the dataset, instead of relying on per-batch DataLoader iteration and repeated dataset indexing. In our codebase, the training data for dino is already returned as a torch.utils.data.TensorDataset (datasets.py, lines 41--54). and selected via get_dataset("dino") returns dino_dataset (datasets.py, lines 57--61).; the baseline training path consumes it through a standard DataLoader (ddpm.py, lines 239--247).. The optimized path bypasses this iterator/indexing machinery and forms batches by slicing the underlying tensors (with equivalent batching and shuffling intent), removing high-frequency __getitem__/generator activity from the hot path and leaving forward diffusion, model forward, loss, backward, and optimizer step as the dominant per-iteration work.

## Runtime results

## Trade-offs and limitations

This optimization improves runtime by reducing Python-side input overhead, but it comes with two practical trade-offs. First, it slightly increases memory pressure by keeping the dataset explicitly materialized and actively accessed as contiguous tensors; in our run this appears as a small increase in RSS (Table ). Second, it reduces generality and scalability: the approach assumes the dataset fits in RAM and bypasses the standard DataLoader pipeline, which is typically required for large or disk-backed datasets (streaming, multi-worker prefetch, online transforms, pinned memory for GPU transfers). As a result, the optimization is well-suited for small in-memory datasets and for isolating training-loop overhead, but it may not transfer directly to realistic large-scale data pipelines.

## Hyperparameter Configuration Recommendations

## Recommended Configurations

Among the 64 evaluated configurations (Table ), a single setup consistently emerges as the most effective across multiple criteria. The configuration bs128_h256_l3_emb128_t100 achieves the lowest final loss (0.474) while maintaining a moderate training time of approximately 1.25 seconds per epoch (Table ). This represents a 38% improvement in loss relative to the average configuration, while being 42% faster than the mean training time.

For scenarios where rapid iteration is the primary objective, such as early-stage development or debugging, a faster configuration using a larger batch size (bs256_h128_l3_emb64_t50) reduces training time to 0.76 seconds per epoch. However, this speedup comes at the cost of significantly degraded convergence, with final loss values approximately 40% worse than the best-performing configuration.

Overall, the benchmark indicates that an intermediate batch size combined with sufficient model capacity offers the most favorable balance between computational efficiency and training quality.

## Key Hyperparameter Effects

The batch size is the dominant factor controlling training speed (Table ). Larger batches maximize throughput and minimize epoch duration, but consistently lead to poorer convergence. In contrast, small batches improve optimization dynamics but incur a substantial computational penalty. A batch size of 128 represents a robust compromise and should be preferred for most use cases. Notably, batch size 64 performs poorly across nearly all configurations and should generally be avoided.

Model capacity is best increased through width rather than depth (Tables and ). Increasing the hidden dimension from 128 to 256 improves convergence by 2.4%, whereas adding additional hidden layers (from 3 to 4) consistently degrades both loss (by 3.2%) and training speed (by 13.5%). This suggests that, for this low-dimensional diffusion task, deeper architectures introduce unnecessary complexity without providing meaningful representational benefits.

The number of diffusion timesteps also plays a critical role (Table ). Increasing the number of timesteps from 50 to 100 improves final loss by approximately 4.3% on average, with a negligible impact on training time per epoch. This makes longer diffusion chains a high-impact, low-cost optimization. Similarly, embedding dimension (Table ) shows a modest 1.9% improvement when doubled from 64 to 128, with minimal computational overhead.

## Architectural Design Principles

From these observations, several data-driven architectural principles can be derived. First, shallow networks with sufficient width outperform deeper alternatives, indicating that architectural simplicity is beneficial for both performance and efficiency. Second, diffusion process configuration—particularly the number of timesteps—has a larger impact on convergence than many architectural parameters. Finally, interactions between batch size and model capacity are non-trivial (Figure ), reinforcing the need to tune these parameters jointly rather than in isolation.

## Training and Framework-Level Optimizations

Beyond hyperparameter selection, the profiler analysis highlights several opportunities for improving training efficiency. The largest limitation of the current implementation is the exclusive use of CPU resources, with no GPU acceleration. Migrating training to GPU is therefore the highest-priority optimization and is expected to yield speedups of one to two orders of magnitude.

At the framework level, a significant portion of training time is spent in PyTorch overhead, optimizer steps, and backward propagation. Techniques such as torch.compile(), mixed-precision training, and fused or optimized optimizers have the potential to reduce training time by an additional 20--40% once GPU execution is enabled.

Taken together, these results suggest a clear prioritization strategy. Immediate gains can be achieved by adopting the optimal hyperparameter configuration and enabling GPU training, which together provide the largest improvements in both speed and performance. Secondary optimizations, such as mixed precision and framework-level compilation, should be applied once GPU execution is in place.

Finally, the benchmark highlights several promising directions for future exploration, including larger batch sizes, longer diffusion chains, and wider network architectures. These extensions are expected to further refine the trade-off between computational efficiency and model quality, particularly in more demanding diffusion settings.

## Conclusion

This study profiled a minimal DDPM training pipeline (tiny-diffusion) to understand where time and memory are spent in iterative diffusion learning. System-level benchmarking revealed substantial orchestration overhead in the end-to-end entrypoint: full_train is 38.3% slower than the minimal core_train baseline. Python-level profiling confirmed that the dominant costs are the backward pass and the MLP forward (linear layers), with additional overhead tied to input construction (concatenations and positional embeddings). A targeted data-path change—batching directly from in-memory tensors instead of repeated DataLoader indexing—reduced wall-clock time by 16.9% with only a negligible RSS increase (<1 MiB), showing that interpreter-side input handling can be a significant bottleneck even in small models.

Hyperparameter benchmarking highlighted a clear quality--speed trade-off: the best overall configuration (bs128_h256_l3_emb128_t100) achieved the lowest final loss while keeping per-epoch time moderate. Across the explored space, wider and shallower networks tended to outperform deeper ones, and increasing diffusion timesteps (50 100) improved convergence with minimal time impact.
